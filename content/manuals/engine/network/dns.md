Docker Engine runs an embedded DNS server for containers connected to
user-defined networks. It resolves the names of other containers on the same
networks, and forwards every other query to upstream DNS servers.

This page describes what the embedded DNS server does, how it chooses and
fails over between upstream servers, and how the `--dns` options change its
behavior. For the per-container flags, see
[DNS services](_index.md#dns-services).

## When the embedded DNS server is used

A container uses the embedded DNS server when it's connected to at least one
user-defined network, such as a network created with `docker network create`,
or an overlay network in Swarm mode.

Inside the container, `/etc/resolv.conf` points at the embedded server:

```console
$ docker run --rm --network mynet alpine cat /etc/resolv.conf
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 127.0.0.11
search example.internal
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(127.0.0.53)]
# Overrides: []
# Option ndots from: internal
```

The embedded DNS server listens on `127.0.0.11`, on both UDP and TCP port 53.
The address is the same in every container, and there is no IPv6 equivalent.
The IPv4 address works even in IPv6-only containers. Applications that need an
explicit DNS server address can use `127.0.0.11`.

The server itself runs inside the Docker daemon, not in the container. Traffic
to `127.0.0.11:53` is redirected to the daemon, so the container never sees the
addresses of the upstream servers.

> [!NOTE]
>
> Containers connected only to the default `bridge` network don't use the
> embedded DNS server. They get a copy of the host's `/etc/resolv.conf`, with
> loopback addresses removed because those only work on the host. If no
> nameservers remain, Docker uses Google's public DNS servers, `8.8.8.8` and
> `8.8.4.4`, plus their IPv6 equivalents when IPv6 is enabled on the network.
> Containers on the default bridge can't resolve each other by name, unless
> you use the legacy [`--link`](links.md) option.

## Names the embedded DNS server resolves itself

The embedded DNS server answers the following queries from its own knowledge
of the container's networks, without contacting an upstream server.

| Query type | Answer                                                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `A`        | IPv4 addresses of a container name, a [network alias](/reference/cli/docker/container/run/#network-alias), or a Swarm service name, on the networks the container is connected to. |
| `AAAA`     | IPv6 addresses, as for `A`.                                                                                                                                                     |
| `PTR`      | The container name for an IP address on one of the container's networks (reverse lookup).                                                                                       |
| `SRV`      | Service records for a published port of a Swarm service, queried in the standard `_<port>._<protocol>.<service>` form. The addresses of the tasks are returned in the additional section. |
| `MX`       | For a name that resolves on the container's networks, an empty successful answer. Mail clients treat this as an implicit `MX` record and use the `A` or `AAAA` records instead. |

If a name has more than one address, for example a Swarm service with several
tasks or several containers sharing an alias, the addresses are returned in a
random order on each query, so that clients spread their connections.

Answers have a time-to-live (TTL) of 600 seconds. The embedded DNS server
itself doesn't cache anything: every query is either answered from the
current state of the networks, or forwarded.

If the name isn't known on any of the container's networks, or the query is
of another type such as `TXT` or `CNAME`, the query is forwarded to the
upstream servers.

## Upstream servers

Queries the embedded DNS server can't answer itself are forwarded to up to
three upstream servers. Where those servers come from depends on whether DNS
servers have been configured explicitly.

- **No explicit DNS configuration** (the default). The upstream servers are
  the `nameserver` entries in the host's `/etc/resolv.conf`, in the order they
  appear. Queries to them are sent from the host's network namespace, so
  loopback addresses such as `127.0.0.53` (`systemd-resolved`) work, and the
  servers are reached the same way the host reaches them.

- **Explicit DNS configuration**, using `--dns` on `docker run`, or `"dns"` in
  `daemon.json`. The upstream servers are the configured servers, in the order
  given. Queries to them are sent from the container's network namespace, so
  the servers must be reachable from the container's networks. An address such
  as `127.0.0.1` refers to the container's own loopback interface, not the
  host's.

  Explicit configuration replaces the host's servers entirely. It's not
  possible to combine servers reached from the host's namespace with servers
  reached from the container's namespace.

- **No usable servers**. If the host's `/etc/resolv.conf` has no nameservers,
  Docker uses Google's public DNS servers, `8.8.8.8` and `8.8.4.4`, plus their
  IPv6 equivalents when IPv6 is enabled.

The comment at the end of the container's `/etc/resolv.conf` lists the
upstream servers in use. Servers reached from the host's namespace are shown
as `host(<address>)`.

Only the first three servers are used. Any further servers are ignored.

### Forwarding and failover

For each forwarded query, the embedded DNS server tries the upstream servers
in order. Each server is given one attempt, with a timeout of four seconds to
connect and receive a response.

The server moves on to the next upstream server when:

- The upstream server doesn't respond within the timeout, or the connection
  fails.
- The upstream server returns `SERVFAIL`.
- The upstream server returns `REFUSED`.

Any other response, including `NXDOMAIN` (the name doesn't exist) and
successful responses with no records, is returned to the container
immediately. A legitimate "no such name" answer from the first server doesn't
cause the other servers to be queried.

If every upstream server fails, the container receives `SERVFAIL`. In the
worst case, with three unresponsive servers, that takes about twelve seconds.

### Internal networks

If a container is connected only to
[`--internal`](/reference/cli/docker/network/create/#internal) networks, it has
no route to the outside world, and the embedded DNS server doesn't forward
queries to upstream servers reached from the host's namespace. Names on the
container's networks still resolve. Servers configured explicitly with `--dns`
are still tried, because they're reached from the container's namespace and
may be on the internal network.

### Limits

Each container's embedded DNS server forwards at most 1024 queries at a time.
Further queries wait for up to four seconds for a slot, and receive `REFUSED`
if none becomes available. A container hitting this limit is usually a sign
that its upstream servers are slow or unresponsive.

Over UDP, responses to queries the embedded DNS server answers itself are
truncated to 512 bytes, or to the size the client advertised with EDNS(0).
Clients retry over TCP when a response is truncated. Responses from upstream
servers are forwarded as received.

## Search domains and ndots

Search domains come from the host's `/etc/resolv.conf`, or from `--dns-search`
if given. Docker adds `options ndots:0` to the container's `/etc/resolv.conf`,
so that container names and aliases such as `db` are looked up as-is rather
than having a search domain appended first.

If you set `ndots` yourself, with `--dns-opt ndots:1` for example, or it's
present in the host's configuration, the embedded DNS server honors it: a
query for a single-label name such as `db` that isn't known on the container's
networks returns an empty successful answer instead of being forwarded. The
container's resolver library then retries with the search domains appended,
which is the standard `ndots` behavior.

## Troubleshooting

To see which upstream servers a container is using, read the comments at the
end of its `/etc/resolv.conf`:

```console
$ docker exec mycontainer tail -n 4 /etc/resolv.conf
# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(127.0.0.53)]
# Overrides: []
# Option ndots from: internal
```

To test resolution from inside a container, query the embedded server
directly:

```console
$ docker exec mycontainer nslookup db 127.0.0.11
```

Names on the container's networks resolve even when upstream servers are
unreachable. If external names fail but container names work, the problem is
with the upstream servers or the path to them.

The daemon logs the details of each forwarded query at `debug` level. To
enable debug logging, see
[Read the daemon logs](../daemon/logs.md).
